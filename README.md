## ข้อมูลและสูตร

`public/sales.csv` — 1 แถว = 1 รายการสินค้า, 1 บิลมีได้หลายแถว
สูตรทั้งหมดอยู่ใน [`src/lib/metrics.js`](src/lib/metrics.js)

- ยอดขาย = `qty × unit_price`
- จำนวนบิล = จำนวน `order_id` ที่ไม่ซ้ำ (ไม่ใช่จำนวนแถว)
- เฉลี่ยต่อบิล = ยอดขายรวม ÷ จำนวนบิล
- ลูกค้าสมาชิก = `customer_id` ที่ไม่ซ้ำ ไม่นับค่าว่าง
- วันที่/ชั่วโมง ตัดจากข้อความ `datetime` ตรง ๆ (ไม่แปลงเป็น UTC จึงไม่เลื่อนวัน)

## การบ้าน: จำนวนบิลตามชั่วโมง — ข้อสังเกต

1. **สาขาออฟฟิศ/ชุมชนขายดีตอนเช้า** — สีลมพีค 08:00 น. (1,241 บิล), อารีย์พีค 08:00 น. หลัง 17:00 น. สีลมแทบไม่มีลูกค้า → เพิ่มพนักงาน 07–10 น. และเปิดสั่งล่วงหน้าผ่านแอป
2. **สาขาในห้างพีคบ่ายถึงเย็น** — สยามและบางนาพีค 16:00 น. ยอดสูงต่อเนื่องถึง 19:00 น. แต่ก่อน 10:00 น. เงียบ → จัดกะหนักช่วง 12–19 น.
3. **มหาวิทยาลัยพีคเที่ยง** — 12:00 น. รองลงมา 15:00 น. ตรงกับเวลาพักนักศึกษา → โปรฯ เซ็ตเที่ยง/บ่าย เตรียมของให้พอก่อน 12:00 น.
4. **ภาพรวมพีค 12:00 น. และ 15:00–16:00 น.** — แต่ถ้าดูภาพรวมอย่างเดียวจะไม่เห็นว่าแต่ละสาขาพีคคนละเวลา → ตารางพนักงานต้องแยกรายสาขา

### Security Rules — ทดสอบกับฐานข้อมูลจริงแล้ว ผ่าน 14/14 ข้อ (`npm run test:rules`)

| กรณี | ผล |
|---|---|
| ยังไม่ล็อกอิน: อ่าน / เพิ่ม | ❌ ปฏิเสธ / ❌ ปฏิเสธ |
| ล็อกอินแล้ว: อ่าน / เพิ่มยอดขายที่ถูกต้อง | ✅ อนุญาต / ✅ อนุญาต |
| qty = -5, 0, 1.5 | ❌ ปฏิเสธ |
| revenue ≠ qty × ราคา · สาขาที่ไม่มีจริง · field แปลกปลอม | ❌ ปฏิเสธ |
| บันทึกในชื่อคนอื่น (`created_by` ไม่ใช่ uid ตัวเอง) | ❌ ปฏิเสธ |
| แก้ไข / ลบรายการ · เขียน collection อื่น | ❌ ปฏิเสธ |

### ความลับ
- Firebase web config (`VITE_FIREBASE_*`) อยู่ใน `.env.local` — เปิดเผยในหน้าเว็บได้ตามการออกแบบของ Firebase ความปลอดภัยจริงคือ Security Rules
- Service account key เก็บไว้ **นอก repo** อ้างอิงผ่าน `SERVICE_ACCOUNT_PATH` ใน `.env.local` · `.gitignore` กันไฟล์ key และ `.env.local` ไว้แล้ว — ไม่มี key อยู่ใน GitHub
